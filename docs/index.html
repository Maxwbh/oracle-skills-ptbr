// compatibilidade

Padrão é a versão para a qual o código sai quando você não informa outra. Mínimo é a menor versão que as skills tratam. Testado diz o que foi executado de fato — o resto é revisão contra a documentação oficial, não garantia de funcionamento em qualquer combinação.

// exemplos de uso

Pedidos típicos e o que cada skill está instruída a entregar. Os itens vêm das regras escritas no SKILL.md de cada uma — não são respostas gravadas; a resposta real depende do seu código e do contexto.

oracle-tuning-ptbr

Query lenta sem recurso pago

"Analise o plano desta consulta no 19c, aponte os gargalos e recomende melhorias. Não tenho Diagnostics Pack."

A skill deve

  • medir antes de otimizar: tempo e plano real do cursor (DBMS_XPLAN.DISPLAY_CURSOR);
  • olhar bind variables e hard parse antes de propor índice;
  • checar estatísticas e histogramas quando a cardinalidade estimada destoa da real;
  • não usar AWR/ASH: sem Diagnostics Pack, fica em V$SQL e V$SESSION.

oracle-apex-ptbr

Código APEX sem versão informada

"Crie um processo que bloqueie a aplicação antes do deploy e libere depois."

A skill deve

  • avisar em uma linha que considerou APEX 26.2;
  • usar APEX_APPLICATION_ADMIN.LOCK_APPLICATION / UNLOCK_APPLICATION (novas no 26.2);
  • dar a alternativa para 24.2/26.1, onde essas APIs não existem;
  • não fazer COMMIT dentro do processo APEX.

oracle-dba-ptbr

Sessão travada em produção

"Tem uma sessão bloqueando o fechamento. Quem é e posso matar?"

A skill deve

  • montar a árvore de bloqueio (em RAC, com GV$SESSION e INST_ID);
  • identificar módulo e usuário da sessão bloqueadora;
  • pedir confirmação antes do KILL SESSION e explicar o rollback que ele causa.

oracle-devops-ptbr

Pipeline com aprovação em produção

"Monte um GitHub Actions que faça deploy em dev, hom e prod, com aprovação em prod."

A skill deve

  • usar GitHub Environments dev/hom/prod com revisor obrigatório em prod;
  • validar os .sql e rodar o CodeScan antes de tocar no banco;
  • executar pelo SQLcl e falhar se o deploy deixar objeto inválido (ALL_ERRORS);
  • nunca pedir confirmação interativa em CI (--confirmar-prod).

// como instalar

⬇ Instalação no Claude.ai

  1. Baixe os arquivos .skill da versão mais recente ou pelos links de cada card. Não há pacote único: é um arquivo por skill.
  2. No Claude.ai → Settings → Skills → arraste o arquivo ou clique em Upload.
  3. Repita para cada skill. Recomendado: todas as 10; no mínimo, oracle-core-ptbr + as skills das tecnologias que você usa.
  4. Teste — peça ao Claude: "Crie um package Oracle para processar pagamentos seguindo Trivadis".

🔄 Atualização

  • Remova a versão antiga da skill em Settings → Skills e envie o .skill novo.
  • Atualize o conjunto todo: as skills citam umas às outras pelo nome e pela versão da suíte.
  • Mudanças incompatíveis estão no CHANGELOG. Na 4.2.0: APEX 26.2 passa a ser o padrão de geração de código.

🧩 Dependências fora do Claude

  • As skills em si não instalam nada: são instruções, referências e templates.
  • Para rodar os scripts da oracle-devops-ptbr: SQLcl no PATH (ou SQLCL_BIN), Python 3 e pip install -r requirements-devops.txt.
  • CodeScan de APEXlang: SQLcl 26.3.0+. APEX 26.2: ORDS 26.3.0+ e banco 19c RU 19.18+ ou 26ai 23.26.0+.

🔒 Verificar a integridade

  • Cada release publica o checksums.sha256 junto dos pacotes. Baixe-o para a mesma pasta dos .skill e rode:
sha256sum --check checksums.sha256
  • No macOS: shasum -a 256 -c checksums.sha256. Cada linha deve terminar em OK.
  • Os pacotes também ficam na pasta dist/ do repositório; o CI confere que ela é igual a um build novo.
